# CM-32P / full CM-64 stage — 2026-08-07

## Scope

Complete Hoot `midiout_type=3` (Roland CM-64) beyond the CM-32L/LA-only Munt
stage by adding a CM-32P-compatible PCM renderer shared by PC-98 and X68000.
The physical CM-64 is treated as two MIDI-visible sound sources in parallel:

- CM-32L / LA section: existing Munt/libmt32emu backend;
- CM-32P / PCM section: new built-in Hoot renderer using user-supplied Roland
  PCM ROM dumps.

The new path deliberately does not redistribute Roland ROMs and does not make
MAME or a CM-32P firmware ROM a build/runtime dependency.

## New software components

New files:

- `src/sound/cm32p_midi_synth.h`
- `src/sound/cm32p_midi_synth.cpp`
- `src/sound/cm64_midi_synth.h`
- `src/sound/cm64_midi_synth.cpp`
- `tests/cm32p_midi_synth_test.cpp`

`Cm32pMidiSynth` implements the existing `MidiSynth` interface. `Cm64MidiSynth`
composes one `Mt32EmuMidiSynth(CM32L)` and one `Cm32pMidiSynth`; every short
MIDI message and SysEx packet is delivered to both sections and their stereo
PCM is summed with clipping protection.

Backend debug kinds are now:

- `0`: none;
- `1`: FluidSynth;
- `2`: Nuked-SC55;
- `3`: Munt MT-32;
- `4`: Munt CM-32L / LA only;
- `5`: full CM-64 composite (Munt CM-32L + Hoot CM-32P);
- `6`: CM-32P PCM section only.

## CM-32P ROM handling

The renderer expects the three original 512 KiB CM-32P PCM dumps:

- IC18 / Roland R15179970, known CRC32 `8e53b2a3`;
- IC19 / Roland R15179971, known CRC32 `c8220761`;
- IC20 / Roland R15179972, known CRC32 `733c4054`.

Known CRCs are preferred. Standard IC/part-number-style filenames are accepted
as a fallback so different preservation naming conventions remain usable.

The raw dumps are address/data-line scrambled. Hoot descrambles them and maps
them into the documented CM-32P logical PCM address space:

- IC18: `000000h-07FFFFh`;
- PCM card: `080000h-0FFFFFh`;
- IC19: `100000h-17FFFFh`;
- IC20: `200000h-27FFFFh`.

The sample table at logical `000100h` and tone table at `001000h` are parsed
directly. The implementation follows the hardware mapping documented by the
BSD-3-Clause MAME CM-32P/Roland LP work and the Roland MIDI implementation
information. Attribution is recorded in `md/LICENSES.md`.

No CM-32P control/firmware ROM is required because this is a high-level MIDI
compatibility renderer rather than a P8098/firmware emulator.

## PCM behavior implemented

The compatibility renderer implements the behavior needed by Hoot MIDI packs:

- six PCM parts, default receive channels 11-16;
- 31 usable PCM voices (32-chip-voice model with firmware-reserved voice 0);
- internal and SN-U110 card tone/sample tables;
- differential PCM decoding with 12-bit-style accumulator saturation;
- 32 kHz reference-note pitch calculation and output-rate conversion;
- normal, no-loop and ping-pong sample modes;
- linear interpolation;
- single, dual, detune, velocity-mix and velocity-switch tone forms;
- program change;
- note on/off;
- modulation, volume, expression, pan and hold/sustain;
- pitch bend plus RPN bend range;
- reset/all-notes/all-sound controller handling;
- six-part voice reservation / voice stealing;
- patch temporary, patch memory and system Roland DT1 SysEx writes;
- Roland checksum validation;
- system master tune, master volume, receive-channel assignment and basic
  reverb parameters;
- CM-32P pan orientation (127 left, 0 right).

Attack/release response, LFO/vibrato, reserve arbitration, interpolation and
reverb are modeled at a useful compatibility level. They are not claimed to
be cycle-, firmware- or analog-hardware-exact. Full hardware verification is
outside this stage; even current MAME labels its CM-32P machine not working /
imperfect sound, so Hoot intentionally uses a smaller high-level path instead
of embedding an incomplete machine emulator.

## SN-U110 card selection

`hootplay.ini` now supports:

```ini
[midi]
# cm32p_rom_path = roms/cm32p
# cm32p_card_rom = roms/cm32p/SN-U110.bin
# cm32p_card_rom_07 = roms/cm32p/SN-U110-07.bin
# cm32p_card_rom_10 = roms/cm32p/SN-U110-10.bin
```

Environment equivalents:

- `HOOT_CM32P_ROM_PATH`
- `HOOT_CM32P_CARD_ROM`
- `HOOT_CM32P_CARD_ROM_07`
- `HOOT_CM32P_CARD_ROM_10`

The generic card path remains the fallback. The X68000 and PC-98 MIDI setup
inspect the catalogue title: variants that explicitly name `SN-U110-07` or
`SN-U110-10` automatically request the corresponding configured card ROM.
This matters for the current X68000 catalogue, which contains three named card
variants: one `-07` and two `-10` entries.

## Backend selection

For `midiout_type=3`:

- `[midi] backend=auto`: try full CM-64 first; if CM-32P ROMs are absent, keep
  the previous Munt CM-32L/LA-only fallback and expose a warning;
- `backend=cm64`: require the full composite;
- `backend=cm32p`: render only the PCM section, useful for diagnostics;
- `backend=munt`: intentionally keep CM-32L/LA only.

Type 1/2 MT-32 behavior and type 4/7/8 GM/GS behavior are unchanged.

## Master tune correction

During final review the CM-32P system master-tune conversion was corrected.
The documented value range maps to 432.1-457.6 Hz; Hoot now converts that
frequency range to cents around A4=440 Hz. The earlier provisional linear
3.125-cents-per-step approximation was too wide.

## Tests

The test suite increases from 13 to 14 tests.

`cm32p_midi_synth_test` builds synthetic logical PCM/tone tables, scrambles
three 512 KiB images back into the raw dump layout, and verifies that Hoot can
recover and play them. It tests:

- internal ROM discovery and descrambling;
- default channel 11-16 behavior;
- note generation and PCM output;
- reversed CM-32P pan convention;
- Roland DT1 system receive-channel reassignment;
- invalid Roland checksum rejection;
- SN-U110 card-ROM loading and card tone playback;
- full CM-64 composition with the ABI-compatible mock libmt32emu;
- reset and mixed output.

Final test results on the definitive source:

- Release: **14/14**;
- ASan + UBSan: **14/14**.

No new compiler warning originates from the CM-32P source; the build still
shows the already-existing libvgm flexible-array / macro warnings.

## Existing X68000 MT-32 regression

The complete previous real-pack ABI gate was rerun after adding CM-32P, using
the same eight-second fresh-process-per-track timing. `mock_mt32emu` stands in
only for the final Munt library; the real Hoot X68000 drivers and CZ-6BM1 MIDI
transport execute unchanged.

| Entry | Runs | Audio-active | Note-active | Malformed MIDI |
|---|---:|---:|---:|---:|
| `ad68snd-generic-2` | 22 | 22 | 22 | 0 |
| `ad68snd-generic-3` | 22 | 22 | 22 | 0 |
| `paro68snd-generic-2` | 36 | 36 | 33 | 0 |
| `paro68snd-generic-3` | 36 | 36 | 33 | 0 |
| **Total** | **116** | **116** | **110** | **0** |

Parodius' six non-note-active cases are the same hybrid OPM-only cues from the
previous baseline and remain audio-active. A three-second fresh-process test
is intentionally insufficient for Akumajou Dracula because its large MT-32
initialization SysEx still has to traverse Hoot's emulated 31.25 kbit/s MIDI
wire; the established eight-second gate remains the correct regression test.

## Evidence boundary

No authentic CM-32P/CM-64 Roland ROMs are present in the development
environment, and none of the supplied archives for this stage is one of the
32 catalogue archives with a CM-64 configuration. Therefore this stage has:

- ROM-layout and PCM-synthesis validation with generated fixtures;
- CM-64 integration validation with an ABI-compatible Munt test module;
- Release and sanitizer coverage;
- full regression validation of the existing X68000 Munt paths;

but **not** authentic CM-32P timbre comparison or a real CM-64 pack gate.
Those require user-owned IC18/IC19/IC20 dumps, CM-32L ROMs and one or more real
CM-64 packs.
